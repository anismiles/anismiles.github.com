Whitepaper · Semantic Layer for Agents · September 2026

The AI-Native Semantic Layer

Lattice: a grammar with a memory

Semantic layers were built so that a finite set of questions would get consistent answers. Agents don't ask a finite set of questions. This paper argues that the catalogue of pre-declared metrics — the thing every semantic layer is organised around — is the assumption that breaks, and sets out what replaces it.

1 · The arithmetic that nobody sees go wrong

why this problem is old, and why agents make it new again

Ask an agent how much you sold last quarter and it will tell you. That's the problem.

The number comes back formatted, confident, and backed by a query you can read. There's a decent chance it's wrong by a factor — not because the model is careless, but because SQL over a normalised schema has a trap that doesn't announce itself.

Here's the whole thing in two tables.

Written out, for a join on key k and a measure m defined over R:

SUM over (R ⋈ S) of m  =  Σ  m(r) · |{ s ∈ S : s.k = r.k }|
                          r∈R

That equals SUM over R of m only when every one of those counts is exactly 1. One-to-one joins are safe. Every to-many edge in the schema is a place where a correct-looking query returns a figure inflated by the average fan-out, and neither the database nor the result will mention it.

We solved this a long time ago, and the solution was a person. Someone modelled the warehouse, built the dashboard, checked the total against the finance close, and the dashboard stayed built. A semantic layer is the artifact of that checking — a place to write down, once, which joins are safe and what "revenue" means, so the next dashboard inherits the work.

It worked because the question set was finite. Dashboards are finite. You can enumerate them, and you can enumerate the measures they need, because the measures and the dashboards were designed together, by the same people, in the same quarter.

Agents break the enumeration, not the arithmetic.

An agent doesn't pick from a menu. It decomposes a vague question into six specific ones, half of which nobody anticipated, then composes the answers. Question volume is unbounded and question shape is unpredictable. And the thing that used to catch the fan-out — a person looking at a chart that seemed too big — isn't in the loop. The number is absorbed into a paragraph of prose and acted on.

So agents need a semantic layer more than dashboards ever did. The awkward part is that the semantic layers we have were built for the other job, and they carry an assumption from it that doesn't survive the move.

2 · What everyone built, and what follows from it

four serious systems, one shared architectural commitment

Cube, dbt, Snowflake and Databricks arrived independently at the same core decision: a metric is a named object you declare ahead of time.

Cube

Cubes organise tables and the connections between them. Each carries measures with a fixed type — count, sum, number — and dimensions to slice them by. A measure must exist in the model file before a query can name it.

dbt

Semantic models declare entities, dimensions and simple metrics against a dbt model. A simple metric binds one column to one aggregation — agg: sum — so a second aggregation over the same column is a second metric.

Snowflake

Semantic views are DDL with a required clause order: tables, relationships, facts, dimensions, then metrics last. Facts capture "how much" at the grain; metrics aggregate facts with SUM, AVG, COUNT.

Databricks

Metric views are YAML objects in Unity Catalog that separate measures from the fields you group and filter them by, with composable and window measures layered on top.

Different syntax, same shape — and it's a good shape. Declaring a metric is how you get one number that means one thing across forty reports, and that was the actual job. Cube describes the value as pre-approved metric definitions, which is an honest account of the bargain: pre-approval is what makes the answer trustworthy.

Four consequences follow. None of them were mistakes when the customer was a dashboard.

2.1 The declared set is the answerable set

If nobody declared net revenue per active customer, excluding returns, for cohorts that joined after March, an agent has two options. Decline. Or leave the semantic layer and write SQL against the physical tables — at which point every guarantee the layer existed to provide evaporates, including the one from Figure 1.

dbt makes the binding most explicit of the four. A simple metric is one column plus one fixed agg:, declared together. Want the average of a column you declared as a sum? That's a second metric, a second name, a second review. The catalogue isn't a convenience layer over the data — it is the interface, and its edges are exactly where the system stops.

It's a fence with a single gate, and the gate is marked give up.

You can watch each vendor solving this the same way: put a language model in front of the semantic model and let it generate SQL, with the model as context. Cortex Analyst does this, Genie does this, Cube D3 does this. It's a reasonable response and it genuinely helps — Cortex Analyst generates against the semantic model's logical tables and columns rather than raw physical ones, which is meaningfully safer than nothing at all.

But notice where correctness now lives. It moved out of the execution path and into the generation step. The semantic model became guidance, and guidance is soft. A generated join is a generated join, whatever informed it.

2.2 Joins: solved, for declared metrics

This is the gap somebody has properly closed, and it's worth being exact about it. MetricFlow builds a join graph out of entity types — primary, foreign, unique, natural — and resolves paths across semantic models at query time, deliberately avoiding fan-out and chasm joins rather than leaving them to the caller. Databricks goes a long way in the same direction: define the metric once, group by any available field, and the engine works out the computation.

So the honest version of this gap is narrower than it first appears, and it turns on a single qualifier. MetricFlow protects a measure that was declared — written down, reviewed, compiled. The protection is real, and it is bounded by that word.

Two smaller differences survive. Inferring the graph from key types is elegant, but it makes an edge's cardinality a property of the keys rather than something stated per edge — and where two edges span the same pair of models, a billing address and a shipping address both pointing at one addresses model, you need separate semantic models or separate entity names to tell them apart. And where a path is genuinely ambiguous, a layer can guess or it can refuse. Only one of those shows up in a log.

2.3 Composition is binary

You get a declared measure, which is safe and inexpressive. Or you get generated SQL, which is expressive and unchecked. There's nothing in between — no way to say this agent may compose freely, within these operations, over these columns. Authority is all or nothing, and because "nothing" makes the product useless, in practice it's all.

2.4 What the system learns sits beside the model, not in it

To their credit, everyone noticed this one. Snowflake has a Verified Query Repository — question-and-SQL pairs the generator draws on, plus custom instructions for steering it. Databricks has trusted assets: parameterised example queries and SQL functions that mark a response as verified.

These work. But look at what they are. A data team writes them in advance, from knowledge it already has, scoped to a specific space or model, as material to steer a language model's generation. They're a curation surface.

Which leaves the interesting question open: where does knowledge go when it's discovered — at three in the morning, by an agent nobody is watching?

3 · Columns, not measures

the measure space is generated, not enumerated

The name is borrowed, and precisely. In 1996, Harinarayan, Rajaraman and Ullman described the space of all possible aggregations over a dataset as a lattice of cuboids — every group-by a node, every edge a refinement, the whole thing partially ordered. It's a real mathematical object with real structure.

A cube is one point in that lattice. The systems above ask you, at modelling time, to name the points you'll want later.

Lattice doesn't declare measures. It declares columns, and a column is a row-level expression that hasn't been aggregated by anything:

columns:
  - name: net_revenue
    sql: subtotal - discount
    type: DOUBLE

Aggregation is chosen in the query, spelled with a colon:

net_revenue:sum
net_revenue:avg
net_revenue:sum(window='90d')          # trailing 90 days, per bucket
net_revenue:sum(partition_by=region)   # region total, on every finer row
price:weighted_avg(weight=quantity)
customers.score:avg                    # across a join

Nobody declared any of those. They are the column crossed with the aggregation grammar, and they exist the moment the column does.

Count it. A model with C aggregatable columns and A aggregations exposes C×A base measures before you touch windows, partitions or weights, and before any arithmetic between them. Forty columns is a few hundred measures that nobody had to anticipate, spell, name or review.

Which sounds like giving up exactly what declared metrics bought you. It isn't, because of the next part.

A saved measure is the same expression, saved

measures:
  - name: aov
    formula: net_revenue:sum / *:count
    label: Average Order Value
  - name: aov_mom
    formula: change_pct(aov)

That's the same language the query uses. net_revenue:sum / *:count is something an agent can write inline this afternoon, and something you can save under a name this evening — and the saved version isn't a different kind of object. It's the same string, promoted.

One expression language, two levels of permanence. An agent composes something useful; a human blesses it by naming it; nobody translates between formalisms. And because aov_mom is defined in terms of aov, the vocabulary stacks.

Semantics that must never be forgotten stay on the column, where forgetting isn't possible:

- name: completed_revenue
  sql: subtotal
  filter: status = 'completed'

That desugars to CASE WHEN status='completed' THEN subtotal END in every position it appears — as a measure, inside a filter, in an order clause, nested in a larger expression. An agent can't forget the condition, because applying it was never the agent's job.

The obvious objection

Column-first sounds lower-level. If the model just exposes columns, haven't you handed the agent SQL with extra steps?

No, and the distinction is the whole design. What a column means, which aggregations it admits, what it's masked to, how it joins — all still declared, all still reviewed, all still in the model. The only thing that moved to query time is which aggregation to apply. That is precisely the decision nobody could know in advance, which is why enumerating it was always going to fail.

4 · Prune the lattice, don't fence the question

generative and governed are not a trade

They aren't a trade as long as the constraint goes in the right place — on the grammar, not on the question.

Every column can name the operations it admits:

- name: account_balance
  sql: balance
  allowed_aggregations: [min, max, avg]   # semi-additive: never sum

That's checked when the model is saved, not when a query arrives. The list must be a subset of what the column's type supports, and a primary key is restricted further to the handful of aggregations that mean anything on an identifier. Opaque types can't be aggregated at all. A balance that must never be summed across time is a balance no query can sum — not by convention, not by a reviewer catching it, structurally.

Session · catalogue value
   "What's the total value of our catalogue, by category?"

→  { "source_model": "order_items",
     "dimensions": ["products.category"],
     "measures":   ["products.unit_price:sum"] }

   column 'unit_price'.
     reason: column 'unit_price' restricts allowed_aggregations to
     ['avg', 'max', 'min']; got 'sum'.

     "dimensions": ["products.category"],
     "measures":   ["products.unit_price:avg", "*:count"] }

←  products.category   unit_price_avg   _count
   coffee                       4.112      939
   merch                       21.244      935

Summing list prices is a reasonable first move and a wrong one. Note what the refusal costs: one round trip, and the agent recovers by composing a different measure — unit_price:avg, which nobody declared either. The person ends up being told their question was malformed, which is the outcome §1 said was missing.

The modeller can also extend the grammar itself:

aggregations:
  - name: trimmed_sum
    formula: SUM(CASE WHEN {value} BETWEEN {low} AND {high} THEN {value} END)
    params: {low: 0, high: 1000000}

Now revenue:trimmed_sum is a legal move for every agent, everywhere, with the outlier policy baked in. The modeller adds a verb; the agent conjugates it. That's the graded authority that's missing when the only options are "declared measure" and "raw SQL".

A declared metric list constrains the set of answers. A pruned lattice constrains the set of legal operations — and the answers it admits are enormously more numerous while being no less checked.

Enforcement is structural rather than advisory. Queries compile through an abstract syntax tree into dialect-specific SQL, so there's no string concatenation and therefore no seam where a generated fragment could be spliced in. The agent never produces SQL at all. It produces a request in a grammar, and the model defined the grammar.

When a question can't be answered honestly, the layer says so rather than approximating. Ambiguous references fail with the scope they searched attached. A model whose underlying table has drifted refuses to run against a schema it no longer describes. And where the engine has to alter the intent of a request — normalising an expression, or dropping a filter that couldn't reach inside a subquery — the response carries a machine-readable warning with a kind discriminator, so the agent can branch on it.

That last point is small and load-bearing. A string of SQL has nowhere to put a caveat. A structured response does.

5 · Let the layer find the path

grain selection as a computed property, not a caller skill

Joins are declared once, on the model, with their cardinality:

joins:
  - target_model: customers
    join_pairs: [{customer_id: id}]
    cardinality: many_to_one

After that, nobody names a path again. An agent asks for customers.regions.name and the engine works out how to get there. Traversal runs in both directions. Where two edges span the same pair of models — a shipping address and a billing address both pointing at addresses — named edges disambiguate, and where nothing disambiguates, the query fails rather than guessing.

Then the move that matters most for agents: you can leave the model out entirely.

This is what makes join discovery genuinely agentic rather than merely convenient. An agent doesn't have to know your schema to ask a correct question about it. It names fields. The engine finds the smallest model that determines all of them, runs there, and states in the response which grain it picked and that it picked rather than being told.

And the fan-out from Figure 1?

Because every edge carries its cardinality, the engine knows when an aggregate would cross a to-many boundary. That isn't a lint rule — it changes the generated SQL. A measure whose natural grain is coarser than the query's gets computed in its own isolated subquery at its own grain, then joined back to the result. The multiset the aggregate runs over is correct by construction.

Where the right answer is genuinely ambiguous rather than merely tricky, it becomes a declared policy on the query: broadcast the coarse value down, associate it once, or refuse. And refuse is a default you're allowed to choose.

None of which is novel on its own, and it shouldn't be. MetricFlow has been resolving fan-out from entity types for years, and a semantic layer that doesn't do this in 2026 is simply behind. The harder version of the problem is the one column-first creates for itself. Guaranteeing correct grain for a measure somebody declared, reviewed and compiled is comparatively tractable — you know every measure in advance, so you can check them all. Guaranteeing it for a measure an agent composed thirty seconds ago, out of a column and an aggregation that had never been paired before, is a different claim. That's why cardinality is declared on the edge rather than inferred from key types, and why the ambiguous case resolves to a policy you set rather than a heuristic you inherit: an open measure space has no test suite you can write in advance.

The bug in Figure 1 isn't something Lattice warns you about. It's something the query shape makes unrepresentable.

6 · Memory that belongs to the concept

semantic memory, not agent memory

First, what this isn't. It isn't conversation history. It isn't a scratchpad an agent keeps between turns, or a vector store of past sessions, or anything that belongs to an agent at all. Call that agent memory — it's a different problem, and a reasonably well-served one.

This is memory attached to the semantic graph. A record looks like this:

learning: >
  "Active customer" here means an order in the trailing 90 days,
  not a non-null account. Finance reports the 90-day definition;
  the account-status column lags cancellations by a billing cycle.
entities:
  - shop.customers
  - shop.customers.status
query: { ...a complete, runnable query object... }

Three properties carry the weight.

Addressed to entities, not sessions

Those entities are canonical references into the model graph — a model, a column, a measure. The memory hangs off the concept, not off whoever happened to find it.

Delivered at the point of contact

When an agent inspects customers, the learnings attached to customers render inside the model card, alongside the columns and the joins. There's no retrieval step to tune and no similarity threshold to get wrong. The knowledge is simply there, in the thing the agent was already reading.

Executable, not merely descriptive

A memory can carry a full query object rather than a SQL string, so precedent doesn't get described — it runs. Those surface as example queries during search. Memories also reference one another, with cascade on delete, so what accumulates is a graph laid over the semantic graph: definitions pointing at the caveats that qualify them.

So how is this different from a verified query repository? Precisely — and it's worth being precise, because the surfaces look superficially alike.

A VQR and a set of trusted assets are curation: written ahead of time, by humans, from knowledge they already have, scoped to the assistant that will consume them, as material for a generation step. That's useful, and any serious system wants it.

What Lattice adds is a learning surface. It's written at the moment of discovery, by whoever discovers it — a modeller, an analyst, or an agent mid-task that has just worked out why two revenue figures disagreed. It's addressed to the concept rather than to the assistant, so it outlives the session, the agent, and the product the agent was part of. And the next reader doesn't have to go looking, because it arrives attached to the thing it's about.

The loop is unremarkable in operation, which is the point.

Session · March → September
── March · an agent reconciling two reports ──────────────────────

→  POST /memories
   { "learning": "\"Active customer\" here means a completed order in
                  the trailing 90 days, not a non-null signup_date.
                  Finance reports the 90-day definition.",
     "linked_entities": ["shop.customers"] }

←  { "memory_id": "3", "resolved_entities": ["shop.customers"] }

── September · a different agent, a different product ────────────

   "How many active customers do we have in each region?"

→  inspect(reference="customers", entity_type="model")

←  # Model: `customers`
   ## Columns (6 — names only)
   `id`, `name`, `email`, `region_id`, `signed_up_at`, `loyalty_tier`
   ## Joins (2 — names only)
   `regions`, `orders`
   ## Learnings (1)
   - **M3** (`shop.customers`): "Active customer" here means a
     completed order in the trailing 90 days, not a non-null
     signup_date. Finance reports the 90-day definition.

Real output; sampled values and data profile elided.

The September agent reached for customers, saw signed_up_at, and would have used it. The learning intercepts that before a query is written — and it arrives because the agent opened the model, not because it went looking for advice. There is no retrieval call in that transcript, no similarity threshold, no memory tool.

Hand the layer a query instead of a list of entities and it works out the concepts itself:

→  "linked_entities": { "source_model": "customers",
                        "dimensions": ["region_id"],
                        "measures": ["orders.net_revenue:sum(window='90d')"] }

←  { "memory_id": "2",
     "resolved_entities": [ "shop.customers",
                            "shop.customers.region_id",
                            "shop.orders.net_revenue" ] }

Nothing was tagged. The memory is addressed to three entities because the query touched three entities, and it carries that query with it — so the precedent doesn't have to be described, it runs.

Nobody wrote a data dictionary. Nobody maintained a wiki that went stale within a quarter. The definition lives where the thing it defines lives, which is the only place anyone reliably looks.

Agent memory makes one agent better over time. Semantic memory makes the organisation's model of itself better over time.

Worth saying plainly: this is the only part of the system that improves without anyone planning for it to. Columns are designed. Joins are designed. Memory accrues as a side effect of use — and it's the part that captures the things that were never in the schema to begin with.

7 · What compounds

the argument in three sentences

Columns bound what's expressible. Joins bound what's connectable. Memory records what turned out to be meaningful.

The first two you decide once, carefully, the way you'd decide a schema. The third grows every time somebody uses the thing — which, with agents, is constantly and mostly unattended.

The received wisdom right now is that a semantic layer for AI is a metrics catalogue with a language model bolted to the front. That gets the shape wrong. The catalogue was never the valuable part. It was a compression of a finite question set, and the question set stopped being finite.

What agents need is a grammar they can compose in, bounded by the operations the data actually supports — and somewhere durable to put what they learn, addressed to the concepts rather than to themselves.

A grammar with a memory. That's the whole argument.
