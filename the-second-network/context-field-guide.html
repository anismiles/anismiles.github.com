Context: What Do They Mean When They Say It?

Ten things called context, how they fit together, and which ones matter

In one year, "context" became the most used word in enterprise AI. It now means many different things: the text a model reads, a way to connect tools, a file in a code project, a store of business definitions, a memory system, an investor's pitch and a startup category. This guide separates them, shows how they connect, and helps you tell a real product from a new name.

A note on bias: the author builds data platform software in this area. This page names none of those products and argues for no vendor, including his own. When one vendor criticises another here, both sell in the same market, and we say so.
Who this is for: people who have to judge claims about context, not build it from scratch. Data and platform architects will get most from section 3. Data, AI and technology leaders can start with the map, the decoder and the five tests (sections 1, 2, 4 and 5). AI engineers building agents will find 3.1 to 3.6 most useful. It assumes you already hear these terms at work; it isn't a how-to or a research review.

1 · One word, ten jobs

why the word stopped meaning one thing

Until recently, "context" meant one thing: the text a model can see when it answers. In mid-2025, people started using context engineering as the name for the harder job of choosing that text. Then the word spread. First to the tools that feed models, then to data platforms, then to sales pitches. By mid-2026, O'Reilly said context engineering had replaced prompt engineering as the core skill for building agents, and data platform keynotes were calling agent quality a context problem.

The word now covers at least ten different things. They aren't rival definitions. They sit at different distances from the model, get built at different times, and serve different people. Most confusion starts when someone takes the word from one layer and uses it to sell a product from another.

Read the diagram from right to left. The model only sees the window: the text it gets for one request. Something fills that window for every request, and that job is context engineering. It pulls material through a connection, usually the Model Context Protocol (MCP). The material comes from sources built in advance: procedures, definitions, memory, records of past decisions, and everyday documents and chats. Three points follow.

MCP is not a context strategy. MCP is a pipe. It lets an agent reach a system, but it carries whatever that system holds. If a warehouse has four columns that could each be "revenue" and nothing says which one finance uses, MCP just delivers that confusion faster. Adding MCP without fixing the sources gets you to the same wrong answer, only quicker.

You can't buy context engineering off the shelf. It's work done for every request: picking what goes into the window, in what order, within a fixed size. Tools help. But the result depends mostly on what the sources contain. If the sources are unclear and nobody owns them, the agent's context will be unclear too, however good the code.

A product called "the context layer" is claiming several boxes at once. Such a product claims to cover some mix of the boxes on the left. Check each box separately. Most products are strong in one or two and weak in the rest. Knowing which tells you what else you'll need.

2 · Two questions that sort every use

when is it built, and who is it for

You can place almost any use of the word by asking two questions. First, when is it built? Some context exists only for one request. Some builds up as people use a system. Some is written on purpose, in advance, by someone responsible for it. Second, who is it for? One request, one person or team, or the whole company. Second, the middle column, context learned from use, is the newest and least settled. Memory and decision records hold the hardest problems, and the weakest evidence.

3 · Ten meanings, from the model outward

what each one is, where it comes from, and what to ask

The entries follow the first diagram, starting at the model and moving outward. Each one says what the term means, where it came from, what people mix it up with, and how much you can trust it. Each ends with one question to ask when someone uses the term.

3.1 The context window

Builtper requestServesone requestStandardnone; each model sets its own

The context window is the text a model reads for one request: its instructions, the conversation so far, any documents pulled in, tool results and its own earlier replies. It's measured in tokens (roughly, pieces of words), and it's gone when the request ends. Everything else on this page is a way of deciding what goes into it.

Windows have grown from a few thousand tokens to a million or more. That doesn't solve the problem. Liu and colleagues found that models use facts at the start and end of a long input much better than facts in the middle. People show the same pattern when they recall a list. Chroma's Context Rot study tested 18 models, and every one got worse as the input got longer, even on simple tasks. A bigger window is a bigger desk. It isn't a better filing system.

People often confuse the window with memory. The window lasts for one request. Memory lasts across many. A typical failure: someone pastes in a long policy document, and the one clause that matters sits two-thirds of the way down.

SolidThis is the original meaning, and the only one you can measure directly. If a claim about context can be tested against the window, test it there.

AskWhere in the window does this go, and what did you leave out to make it fit?

3.2 Context engineering

Builtper requestServesone step of a taskStandardnone; it's a practice

Context engineering is choosing what goes into the window for each step of a task. Say you ask an agent why customer churn rose in March. Before the model starts, something has to decide what to include: the churn definition, last month's analysis, the layouts of three tables, a note about a price change, or none of these. It also decides the order, and everything has to fit a fixed size. That choice is context engineering.

The term caught on in June 2025. Shopify's CEO Tobi Lütke said he preferred it to "prompt engineering," and Andrej Karpathy agreed, calling it "filling the context window with just the right information for the next step." Anthropic's engineers describe it as spending a limited supply of the model's attention. LangChain's guide splits the work into four jobs: writing, selecting, shortening and separating context. By 2026 the topic had its own books, including one by Boni García from Manning.

People often confuse it with the sources it draws from. Context engineering spends context. It doesn't create the definitions, memory or records it uses. The typical failure is good assembly of bad material: a well-tuned search that faithfully returns three different definitions of the same number.

Solidas a practice. It's a real engineering skill. Hypeas a product. A "context engineering platform" is usually search or memory tools with a new name, because the actual work happens in each team's own code.

AskIs this something my engineers do, or something you sell? If you sell it, which source from section 1 is it, really?

3.3 The Model Context Protocol

Builtper requestServesany agentStandardMCP, under the Linux Foundation

The Model Context Protocol is an open standard that lets agents connect to tools, data and apps in one common way. Anthropic released it in November 2024. In December 2025, Anthropic handed it to the Agentic AI Foundation, part of the Linux Foundation, which Anthropic, Block and OpenAI set up together. By then there were more than 10,000 public MCP servers, and ChatGPT, Claude, Gemini, Microsoft Copilot, Cursor and VS Code all supported it.

MCP fixed a real problem: before it, every agent needed a custom connection to every system. But the word "context" in its name does a lot of marketing work. MCP carries context. It doesn't create it. A connection to a warehouse tells an agent which tables exist. It doesn't tell the agent which ones finance trusts, or what a column called rev_adj means.

People often mistake MCP for the context it carries. The typical failure: an agent reaches the right system through a good MCP server and still picks the wrong column, quickly and confidently.

Solidas plumbing, and now the default plumbing. "We have an MCP server" tells you an agent can reach the system. It says nothing about whether the answers will mean what your business means.

AskWhat does the agent actually get through this server: raw rows, or definitions it can trust?

3.4 Instructions and procedures

Builtin advanceServesa team or code projectStandardAGENTS.md; Agent Skills

Procedural context tells an agent how work gets done. In software, that's a file like AGENTS.md in a code project, explaining how to build and test it, or a similar file like CLAUDE.md. Agent Skills go further. They bundle instructions with scripts and reference material, and an agent loads them when a task needs them. OpenAI's AGENTS.md went to the same foundation as MCP. The two fit together: MCP gives the agent connections, and procedural context tells it how to use them.

Inside a company, this layer is bigger and mostly unwritten. How does a large refund get approved? Which contract template does legal use for which customer? Who do you call when a shipment is stuck? Research on memory separates knowing that from knowing how. Most writing on context focuses on the first. In the author's experience, agents stumble more often on the second.

People often confuse it with semantic context. Semantic context says what a word means. Procedural context says what to do. The typical failure is drift: two skills that give opposite instructions, or a file that described last quarter's process and never got updated.

Solidand underrated. This is the "how we do things here" layer. It deserves the same ownership and review as code.

AskWho owns these files, who reviews changes to them, and what happens when two of them disagree?

3.5 Semantic context

Builtin advanceServesthe whole companyStandardemerging; mostly tied to each platform

Semantic context is written-down meaning: how each metric is calculated, what the main business objects are (customer, order, contract), and how they relate. A formal version of this is called an ontology. When an agent is asked for last quarter's revenue, semantic context tells it the company means recognised revenue, on the fiscal calendar, after refunds, from the finance model and not the sales one. You write it once, keep versions, and give it to every dashboard and agent, so the same question always gets the same number.

In 2026 every big platform shipped a version. Snowflake let people query its Semantic Views with standard SQL in March. Databricks made Unity Catalog Business Semantics generally available in April, about a month later, and said it would open-source the core in Apache Spark. Microsoft's Fabric IQ adds a model of business objects on top of its data store. A shared standard called Open Semantic Interchange aims to let definitions move between these systems, but one vendor's review found that no product yet supports importing or exporting it.

Keep expectations realistic. Databricks' own agent metadata is display names, formats and synonyms: useful, but modest. People often confuse a semantic layer with a data catalog. A catalog lists what data exists and who owns it. A semantic layer defines how a number is calculated. The typical failure is two systems, each with its own approved definition of the same metric.

SolidThe most mature of the ten, and the easiest to test. Promises of perfect accuracy from definitions alone are slogans, but this is the layer where accuracy is won most reliably.

AskWhere does this definition live when we run more than one system, and who approves a change to it?

3.6 Agent memory

Builtfrom useServesone person or agentStandardnone

Agent memory is what a system learns from use and keeps across sessions: a person's preferences, facts they've shared, earlier answers and corrections. If you tell an assistant your sales region changed, memory should make next week's report use the new one. ChatGPT and Microsoft Copilot have memory built in. Developers can use tools like Mem0, Zep and Letta. By 2026, O'Reilly was calling memory a core part of agent design, not an add-on.

The hard part is saving. A memory system has to decide what to keep, how to fit it with what it already knows, when to let it fade, and what to do when a saved fact turns out to be wrong. Some systems overwrite the old fact. Better ones mark it as out of date and record when it was true. Anything thrown away when saving can't be recovered later. People often confuse memory with semantic context. The difference is who wrote it. Semantic context is written by someone responsible and applies to everyone. Memory is learned, and applies to one person or agent. The typical failure is the stale fact: the old sales region, still used with confidence weeks after the person corrected it.

Solid idea, weak evidenceThe problem is real, but the tests are immature. Most memory benchmarks reward remembering and say little about updates, contradictions or knowing when not to answer. Headline scores often come from press releases that used a different model from the paper they cite.

AskWhen a remembered fact turns out wrong, is it overwritten or marked out of date, and can I see what it used to say?

3.7 Decision traces and context graphs

Builtfrom useServesthe whole companyStandardnone

A decision trace is a record of why an action was allowed: which version of a policy applied, what exception was made, who approved it, and what past case it followed. Picture a vice president approving a big discount on a video call or in a direct message. The CRM shows the final price. It doesn't show who approved the exception or why. A decision trace captures that missing part.

In December 2025, Foundation Capital called the collection of these records a "context graph." It argued that systems which record decisions could become the next big class of business software. The firm's Ashu Garg later measured the opportunity against the trillions companies spend on salaries and services, not against the software market. Not everyone thinks the idea is new. A Finextra essay notes that trading firms have kept decision trails for years, without calling them graphs.

People often confuse decision traces with knowledge graphs. A knowledge graph shows how things relate. A decision trace shows why something happened. A useful trace needs four parts: who made the change, when, why, and what it replaced. Without those, a trace soon becomes no better than a rumour.

Solidas an idea. Systems of record store what happened, not why, and a trail of reasoning is one of the few things a competitor can't rebuild. Hypeas a label. A decision trace doesn't need to be a graph to be useful, and the trillion-dollar sizing is an investor's pitch, not a design.

AskShow me one trace. Who wrote it, when, why, and what did it replace?

3.8 The context layer Bundle

Builtin advanceServesthe whole companyStandardnone

"Context layer" is a claim that one product can give agents what your business means, where the data came from, who may see it and what was decided before, all at the moment they need it. Tellius, for example, lists five parts: definitions, matching the same customer or product across systems, rules for what agents may do, a trail showing how an answer was reached, and memory of past decisions. That's most of the left side of the first diagram. The strips in this entry and the next two show which of those five sources each kind of product usually covers well, so you can compare them.

Catalog and metadata vendors use the term most, and some have renamed themselves outright. OpenMetadata 2.0, released in August 2026, now calls itself an open context layer instead of a data catalog. Vendors are blunt about each other: Strategy and Zaimler both describe the trend as a homepage rename, while each sells its own context layer. DataHub makes the sharpest point: neither a semantic layer nor a context layer creates the trusted information it depends on.

The idea is real when three things are true. The product matches the same customer or product across systems. It checks access on every request, as it happens. And it works with agents from any vendor. People often confuse it with a catalog. Kaelio puts it simply: a catalog helps you find data, while a context layer should control how agents use it. The typical failure is a catalog with an MCP server added, sold as something bigger.

Mostly a new nameThe need is real. The label mostly goes on products that haven't changed underneath.

AskTake away the MCP server. What does this product do that last year's version didn't?

3.9 Platform bundles Bundle

Builtin advanceServesthe whole companyStandardeach platform's own

The biggest platforms now bundle several of these layers under one brand. Microsoft splits it four ways: Work IQ for how people work, Foundry IQ for company documents and policies, Fabric IQ for business data, and Web IQ for the web. Foundry IQ turns company content into knowledge bases that agents can search, with each person's access rules applied. Databricks built its June 2026 conference around the same idea and launched Genie Ontology. CEO Ali Ghodsi said AI's problem is context, not intelligence.

These are real products with marketing names, and they matter more than anything else on this page. Context is moving inside the big platforms. If you run everything on one vendor, that's convenient: definitions, access rules and agents all work together. If you run several systems, or use agents the platform didn't build, you have a portability problem that the brand name won't mention.

People often mistake these bundles for neutral standards. They may use open connections at the edges, but the definitions inside are built for the platform's own agents. The typical failure: a metric defined perfectly in one platform, and invisible to an agent running in another.

Real products, marketing namesJudge each part on its own. The brand name adds nothing.

AskDoes this context work for agents that aren't yours, with the same definitions and the same access rules?

3.10 The company brain Bundle

Builtfrom use and in advanceServesteams and the whole companyStandardnone

A company brain is a system that pulls in documents, chats, meetings and tickets, remembers what it learns, and serves the result to people and agents, with access rules applied. The term took off in 2026. Y Combinator's summer request for startups asked for company brain businesses, startups like Hyper adopted the name, and a company simply called Brain launched in September.

Underneath, it's a familiar mix: company search, memory and access rules over documents and chat. One vendor in the space admits as much, describing it without the marketing as a memory system that learns at company scale.

The name also misleads. The model already does the thinking. What a company lacks is organised, trusted memory for the model to draw on, with a clear line between what someone responsible wrote and what came from a chat thread. The typical failure is losing that line: an agent that can't tell official policy from someone's opinion in a channel.

Mostly marketingThe features underneath are useful. The name describes a hope, not a design.

AskWhich of these answers did someone responsible write, which were learned from use, and can I tell them apart?

5 · Five tests

telling a real product from a new name

The ten meanings are easier to tell apart on paper than in a sales pitch. These five tests work on any claim about context. The first and last catch renamed products. The middle three catch products that are honest but not finished.

Contents. A real product can tell you exactly what it stores and show you how it's organised. A definition has fields. A memory has a structure. A decision trace has parts. "Your company's knowledge" is a goal, not an answer.

History. It should record who added or changed each thing, when, and why. Without that, you can't check it, undo it, or trust it over time.

Access. It should check permissions every time an agent fetches something, not clean up the prompt afterwards. Once an agent has seen a restricted number, you can't make it forget.

Proof. Any claim about accuracy or cost should come with a baseline that someone outside the company could rerun.

Swap test. This one is the fastest. Replace "context" in the product description with "metadata" or "search." If the description still makes sense and nothing sounds new, the word is doing the work, not the product.

6 · What to discount

phrases and numbers that tell you little

Some uses of the word tell you almost nothing. Ignore trillion-dollar estimates for categories nobody has defined yet. Ignore promises of perfect accuracy: nothing on the map delivers that, and the best products make smaller claims. The same goes for "company brain" as a category, "context layer" on a catalog that hasn't changed, "context engineering platform" on a search tool, and new "IQ" names for old services. None of these means the product is bad. They just don't tell you anything about it.

Be careful with numbers too, because some get passed from post to post without their source. The most quoted one says 60% of analytics agent projects that rely only on MCP will fail by 2028, because they lack consistent definitions. It comes from a Gartner analyst's talk at the firm's 2026 data conference, and it's usually quoted secondhand, in vendor posts. It's a forecast, not a finding. Two vendors each report a 38% accuracy gain: one from giving agents governance information, another from combining context across 522 questions. They may be the same study or two different ones, and nobody has independently repeated either. Treat a vendor's own numbers as a claim until someone else tests them.

7 · What stays open

the problems nobody has solved

Set the marketing aside and the hard problems sit in the middle and right of the map. Four stand out.

When written definitions and learned memory disagree, which one wins? A company's official definition of an active customer might say "bought something in the last 90 days." Meanwhile, a hundred users have told their assistants that, for them, it means "logged in this month." The official definition (3.5) is correct for everyone, but it may be out of step with how people actually work. The learned version (3.6) is closer to daily use, but nobody approved it. Today most systems either ignore memory when a definition exists, or let memory quietly override it. Neither is right. There's no agreed way to decide which should win in which case, or to show a user which one produced the answer they got.

How does a correction become an official definition? Corrections are the best evidence of where official definitions fail. If many people fix the same answer in the same way, the definition probably needs to change. But that path has to be controlled. A company can't let the loudest user, or the one who repeats themselves most, rewrite what revenue means. What's missing is a process: gather corrections as evidence, show them to the person who owns the definition, record the decision with who, when and why (the four parts from 3.7), and publish a new version. Almost no product does this end to end yet.

What may an agent rely on, as opposed to see? Access rules answer a yes-or-no question: may this agent read this row? They handle that well. They don't answer a different question: may this agent treat this number as correct and act on it? A table can be readable but half-finished, out of date, or under review. A person would ask before using it in a board report. An agent usually won't. Closing this gap means attaching a clear statement to data, covering what it means, how fresh it is and what it promises, that an agent can check before it acts. Security teams then need to be able to review that statement and sign it off.

Who serves agents that cross platforms? As context moves inside each platform (3.9), each one serves its own agents well. But most companies run more than one system, and more and more of their agents come from outside: an assistant from one vendor, a coding tool from another, a custom agent built in-house. Those agents need the same definitions, the same access rules and the same memory, wherever they run. Someone has to own that shared layer, and it isn't obvious who. Open standards like MCP help with the connection, but not with the meaning that travels over it.
